§1

Что сделано

1.1Приложение — функциональность
  • Веб-панель (Spring Boot + React) для функциональных администраторов — управление и запуск скриптов (PowerShell/Python), включая выдачу прав доступа на счета для эталонных ролей
  • Аутентификация JWT, роль «подтверждающий изменения» для согласования критичных операций
  • История действий и входов (audit trail), выгрузка в CEF (ArcSight) для SIEM с читаемой датой в rt=
  • Мониторинг ресурсов backend/frontend (CPU, RAM, диск, БД, статика) с автообновлением раз в 10 секунд
  • Индикация пользователей онлайн
  • Выгрузка логов: backend, frontend, access-логи nginx, CEF — единое именование (дата + тип), без искажения кодировки
  • Редактирование скриптов прямо в браузере (/admin/scripts) с резервной копией .bak
  • Security-hardening: секреты только через переменные окружения, non-root контейнер backend, rate limiting на логине, security-заголовки nginx
1.2Git-репозиторий, доступ и владение
  • Создан git-проект, разработка ведётся в GitHub (XMD5X/NRD, ветка main)
  • Создан корпоративный проект в GitLab (gitlab.dev002.local/Smolinag/nrd-business-panel), настроен доступ
  • Проект переведён под корпоративную СУЗ — доступ управляется централизованно, больше не завязан на одну личную учётную запись
1.3CI/CD
  • Пайплайн зеркалирования GitHub → корпоративный GitLab, с защитой собственного .gitlab-ci.yml от затирания при синхронизации
  • Подключён общий CI-шаблон организации — сборка проходит корпоративный SonarQube-чек
  • Настроена доставка собранной версии до тестового контура
  • Добавлены job'ы сборки образов (kaniko) и деплоя в Kubernetes (helm upgrade) — пока ручные
1.4Перевод под Kubernetes
  • Полный комплект манифестов: Namespace, Secret, ConfigMap, StatefulSet (postgres), Deployment (backend, web), PVC, Ingress
  • Доведено до Helm-чарта: версионируемые релизы, параметры через values.yaml, HPA (web), PodDisruptionBudget, NetworkPolicy, security-контексты контейнеров
  • Архитектурные ограничения задокументированы осознанно, не заметены под ковёр (см. §3)
  • Подан merge request на создание Kubernetes-кластера в dev — ожидает согласования
  • Текущий стенд развёрнут в корпоративной среде на dev-контуре
1.5Согласования
  • Направлено официальное письмо в ИБ с описанием решения, архитектуры и ссылкой на репозиторий
  • Получен ответ ИБ — проект согласован, дальнейшая разработка разрешена
  • MVP продемонстрирован бизнесу — готовность работать подтверждена; согласование пройдено с обеих сторон
1.6Документация
  • HLD (архитектура и инфраструктура), описание backend и frontend, модель данных
  • Обзор ИТ-решения и customer journey map (несколько версий по мере доработки)
§2

В работе / ожидает решения извне

MR

Kubernetes-кластер в dev

Merge request подан, ждём согласования инфраструктурной команды. До этого момента развернуть приложение в k8s нельзя чисто технически — самого кластера ещё нет, хотя весь набор манифестов и Helm-чарта уже готов.

Согласование с ИБ на данный момент получено (см. §1.5). Если по его итогам ИБ выдвинула конкретные условия или требования к архитектуре (например, по схеме генерации и подтверждения пакетов ЭЦП) — они дописываются сюда и переносятся в §3, как только известны в деталях.
§3

Что осталось сделать

3.1Kubernetes — после получения кластера

Плановая последовательность шагов — по порядку, каждый следующий зависит от предыдущего.

1

Установить приложение в dev-кластере (helm install) сразу после его создания — развернуть Helm-чарт, завести секреты (пароль БД, JWT), настроить values.yaml под конкретный кластер.

2

Подтвердить/настроить ReadWriteMany storage class — без него не заработают access-логи nginx (общий том между backend и web).

3

Настроить постоянный TLS-сертификат на Ingress через cert-manager или корпоративный CA (сейчас в манифестах — заглушка под самоподписанный сертификат).

4

Настроить git (CI/CD-пайплайн) на работу с k8s-кластером после развёртывания стенда — донастроить доступ CI к кластеру и registry (переменные KUBE_CONFIG_B64, DOCKER_AUTH_CONFIG — ещё не заведены), чтобы job'ы сборки и деплоя вообще могли достучаться до dev-кластера.

5

Провести тестовый пайплайн на развёртывание в dev-контуре — запустить job Deploy (helm upgrade) из GitLab CI (не просто helm install руками, как в шаге 1) и убедиться, что автодеплой через git реально работает end-to-end.

6

Проверить работоспособность приложения в dev-кластере — стенд в Kubernetes должен работать так же, как текущий docker-compose стенд.

7

Если проверка успешна — оформить ЗнИ на мощности и сетевые связности для test- и prod-контуров. До успешной проверки в dev заявка на test/prod не подаётся.

8

После выделения мощностей — переписать CI/CD-пайплайн под автодеплой. Сейчас job'ы сборки и helm upgrade ручные — для test/prod нужен автозапуск с раздельными values-<contour>.yaml, namespace и переменными доступа под каждый контур.

3.2Архитектура приложения
  • Горизонтальное масштабирование backend (сейчас жёстко 1 реплика): онлайн-статус пользователей — из памяти процесса в общее хранилище (БД/Redis), синхронизация записи файлов при редактировании скриптов. Нужно, только если потребуется больше одной реплики.
  • Если согласование ИБ содержало конкретные условия к архитектуре — внести их сюда по мере уточнения.
3.3Эксплуатационная готовность — пока не начато
  • Мониторинг и алертинг приложения и кластера (Prometheus/Grafana или корпоративное решение)
  • Резервное копирование и восстановление БД (Postgres) в k8s
  • Нагрузочное тестирование перед переводом в прод-контур
  • План перехода dev → test → prod после согласований и нагрузочного тестирования
  • Внешний secret-manager (Vault / External Secrets Operator), если потребует политика ИБ
§4

Риски и открытые вопросы

  • Сроки перехода в Kubernetes зависят от согласования и фактического создания кластера инфраструктурной командой — вне зоны контроля проектной команды.
  • Наличие подходящего ReadWriteMany storage class в целевом кластере пока не подтверждено — от этого зависит доступность выгрузки access-логов nginx в k8s-варианте.
